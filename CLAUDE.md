# Datathon ForteBank: детекция нарушений кассовой дисциплины по видео

Начали 17.10.2026, дедлайн сдачи — см. ТЗ FAQ 33 (12:00). Пользователь — ML-инженер команды (Жус).
Команда: Богдаг, キラ, gercou, cl0rex1 — разметка и разбор видео.

## Задача в двух словах
Локальный веб-сервис: загружают .mov с кассовой камеры (верхний ракурс, одна камера, звук отсутствует,
10–145 с, ~30 fps, 464×848) → сервис находит признаки нарушений кассовой дисциплины → отдаёт вердикт,
тип, точный таймкод, 1–3 кадра-доказательства, обоснование и пункт НПА РК. Есть публичный API — через него
жюри прогоняет тестовые видео. Всё работает полностью локально.

## Жёсткие ограничения (дисквалификация/потеря баллов)
- Полностью локально: ни одного облачного AI/API (LLM, мультимодалки, распознавание) — даже кадры им передавать нельзя; после загрузки весов — без интернета.
- Лица не распознавать и не идентифицировать (FAQ 29). Звук отсутствует в принципе (FAQ 28).
- Формат .mov, файл ~29 МБ (FAQ 25); обработка одного видео ≤ 5 минут (FAQ 14), иначе «необработано».
- Тестовые видео не использовать для обучения, не публиковать.
- Нормативка — только РК (FAQ 30); ссылки без точного пункта принимаются (FAQ 31), но баллы за точность.
- Нарушения «по бездействию» — таймкод на усмотрение команды (FAQ 10).
- В датасете НЕТ нарушений, основанных только на внутренних правилах ForteBank (FAQ 32).
- Сервис не должен утверждать то, что требует невидимых на видео данных (раздел 7).

## API-контракт (ТЗ раздел 10) — единственная точка проверки жюри
- `Authorization`: заголовок **X-API-Key** (команда создаёт ключ сама, отдаёт жюри).
- `POST /api/v1/analyze` — поле `file` (.mov) → `{"job_id": "..."}`.
- `GET /api/v1/jobs/{job_id}` — `status: processing|done|failed`; при done:
```json
{
  "job_id": "...", "status": "done",
  "verdict": "no_violation" | "violation",
  "violations": [{
    "type": "Название типа нарушения",
    "timecode_sec": 44.2,
    "description": "что видно и почему это может быть нарушением",
    "evidence_frames": [{ "timestamp_sec": 44.2, "image_base64": "<JPEG base64>" }]
  }]
}
```
- В одном видео нарушений может быть несколько → всегда список, не один таймкод.
- Схема результатов: только «Нарушение не обнаружено» / «Обнаружены признаки возможных нарушений».

## Стратегия (согласовано командой, уточнена 17.10 вечером)
- Прогон детекции — всегда по всему видео (батч ≤5 мин): триггер не «включает» проверку, а лишь помечает визит.
- Нейросеть видит ТОЛЬКО примитивы (объекты/состояния/события — словарь в rules_tree.html); supervised-слой —
  только нейтральные события (один ракурс, одни люди — иначе переобучение).
- Вердикт выносит детерминированный движок (`pipeline/`): один проход правил по таблице фактов. Правила — данные
  двух видов: order (порядок действий внутри визита: R1, R4, R6, R10) и streak (инварианты фона по всему ролику:
  R2, R3, R5, R7, R8, R9). Сессии = интервалы-контексты из client_present; стык сессий — самостоятельный источник
  событий (Х-47). Совпадение примитивов вне известных правил → редкий тип «признак, требует проверки» (FAQ 9).
- Движок калибруется на рукописных таблицах фактов (`fixtures/`, из annotations_team.csv) ДО готовности детектора;
  τ — так, чтобы 20 чистых видео давали 0 ложных в ОБЕИХ семьях правил (пропуски хуже ложных, FAQ 16).
- Детектор — Apache-2.0 стек (RF-DETR/D-FINE + supervision): FAQ 24 требует лицензию под коммерческое
  использование; ultralytics (AGPL) — только как инструмент разметки вне поставки.
- Лиц не используем; роль (кассир/клиент/инкассатор/посторонний) — по позиции относительно узла.
  Одиночный кадр врёт: событие = устойчивое состояние на сглаженном треке. Real-time — режим развития/питча,
  не жюрейский путь.
