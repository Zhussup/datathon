# Для презентации: словарь примитивов и дерево решений

> Материал для слайдов. Всё нижесказанное — проверенные факты о системе, не декларации.

---

## 1. Словарь примитивов — и он ДОПОЛНЯЕМЫЙ (обязательно сказать)

**Что это.** Нейросеть (детектор, Apache-2.0) возвращает не «нарушения» и не «роли»,
а список **нейтральных примитивов** — объектов и событий с каждого кадра:

- объекты: `banknotes` (купюры), `document` (документ), `money_bag` (сумка инкассации),
  `safe` (сейф), `stamp` (штамп), `terminal` (терминал), `outerwear` (верхняя одежда),
  `person` (люди — из общедоступной COCO-модели);
- события-переходы: «деньги появились на столе», «документ появился», «человек вошёл» и т.п.

**Почему нейтральность принципиальна.** Модель не обучена на «нарушениях» — она учится
видеть «купюры» и «сейф». Это снимает переобучение (тренировочных нарушений мало,
один ракурс, одни люди) и правовой риск: система не «судит», а констатирует видимое.

**Ключевой тезис для слайда: словарь открыт на расширение.**
Добавить примитив = размечать новый класс + дообучить детектор; **дерево решений
переписывать не нужно** — правило, которое ссылается на новый примитив, добавляется
парой строк в данные правил. Уже спроектированные «следующие»-классы:
`door_open`, `key_in_lock`, `bag_on_desk`, `count_start` (в W3 событие уже есть), `drink`.

Это же прямой ответ на FAQ организаторов «что если в тесте неизвестные типы нарушений»:
движок честно отдает редкие совпадения примитивов как «признак, требует проверки»,
вместо выдумывания типа или молчания.

## 2. Дерево решений — абстрактно (как объяснять со сцены)

Готовая метафора: **«не один судья, а сто маленьких инспекторов с бумажками»**.

Абстрактно решение проходит четыре шага, повторённых независимо для каждого правила:

```
триггер  →  условия (врата)  →  событие  →  сведение (merge)  →  вердикт
```

1. **Триггер** — дешёвое наблюдение: «в таблице фактов появился banknotes на столе»,
   «закончилась сессия обслуживания», «человек вышел из кадра». Триггер лишь
   маркирует место, где стоит вопрос, — он НЕ включает и НЕ выключает проверку.
2. **Врата-условия** — содержательные вопросы, которые могут ответить «нет» и закрыть
   кейс: «документ появился ДО передачи денег?», «кассир ушла более чем на N секунд?»,
   «после ухода клиента банкноты остались на столе?». У каждого правила свой порог —
   и пороги это ДАННЫЕ (таблица ручек Config), а не код.
3. **Событие** — если все врата пройдены, правило порождает конкретный вывод:
   тип + таймкод + кадры-доказательства + пункт НПА (или честное «признак,
   требует проверки» — если прямого пункта в открытых актах РК нет).
4. **Сведение** — событие одного правила и того же типа в пределах нескольких секунд
   склеивается в одно; события РАЗНЫХ правил не гасят друг друга, а накапливаются
   в итоговом списке нарушений. Поэтому дубликат ролика с двумя событиями даёт
   список из двух, а не один таймкод.

**Два семейства правил** — сказать обязательно, это несёт архитектуру:

- **последовательности (order):** проверяют ПОРЯДОК действий внутри одного визита
  («идентификация — потом деньги», «приём — потом пересчёт — потом хранение»);
- **инварианты фона (streak):** проверяют постоянные состояния всего ролика
  («ценности не остаются без присмотра дольше N секунд», «на столе нет личных вещей»).

**Что это даёт (формулировки для слайдов):**

| Свойство | Как звучит |
|---|---|
| Прозрачность | любая строчка вердикта разматывается до «что увидел детектор → какое условие → какой пункт НПА» |
| Легкая калибровка | пороги — таблица; подкрутить = поменять число, не переписать модель |
| Расширяемость | новый примитив → новые правила; старые не переписываются |
| Честность | на каждое утверждение есть кадр; про невидимое система не утверждает |

**Одна фраза на случай вопроса «а почему не нейросеть решает»:**
«Нейросеть видит только факты ("купюра на столе"), а вердикт выносит детерминированное
дерево правил — вывод всегда объясним и привязан к пункту НПА. Обучение на готовых
"нарушениях" переобучалось бы на том, как ВЫ снимаете нарушения».
